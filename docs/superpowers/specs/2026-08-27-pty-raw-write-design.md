# Запись в pty мимо node-pty — на голый fd, с ручной частичной записью

27 августа 2026. Продолжение [BUG-pty-deadlock-2026-08-11.md](../../../BUG-pty-deadlock-2026-08-11.md)
и [pty-write.js](../../../pty-write.js) (коммит `4f717cf`, реализует чанкинг по 256 байт).

## Зачем

11 августа приложение зависло намертво со 100% CPU: один синхронный `live.write()` на несколько
килобайт забил очередь pty, а главный поток, единственный читатель мастера, сам стоял внутри
этого `write()`. Починили чанкингом — `pty-write.js` режет любой текст на порции по 256 байт и
качает их через `setImmediate`, отдавая такт циклу между кусками.

27 августа зависание повторилось на полностью пропатченной сборке (`payload/0.55.1.asar`,
чанкинг подтверждён побайтовым сравнением с рабочим деревом) — но по другому пути: не через
`restartFire`, а во время обычной работы вкладки. Симптом тоже другой: не главный поток
100% CPU из-за перерисовки ZLE, а сам агент спал 0% CPU и не читал терминал, ожил сразу после
`tcflush`.

Причина — не в размере одного `write()`, а в том, КАК node-pty его делает. `UnixTerminal.write()`
(`node_modules/@homebridge/node-pty-prebuilt-multiarch/lib/unixTerminal.js:171`) идёт через
`this._socket.write(data)`, где `_socket` — `tty.ReadStream` поверх fd мастера, то есть
`net.Socket`-подобный поток. Если ядро принимает запись не целиком (частичная запись — обычное
дело для character-девайса вроде pty, когда читатель не поспевает), `uv_write2` внутри libuv
сам, на C++-уровне, доедает остаток внутренним ретраем — и, судя по стеку из баг-репорта
(`uv_write2 → uv_try_write2 → write`, 3506/3623 сэмплов) и по живой репродукции (см. ниже), этот
ретрай не отдаёт такт циклу событий. Чанк в 256 байт эту проблему не устраняет — он лишь снижает
шанс того, что ЛЮБАЯ отдельная запись попадёт в момент, когда очередь ядра уже почти забита; если
читатель не читает достаточно долго (по любой причине, не только из-за эха ZLE), забьётся и
256-байтный кусок.

## Живая проверка (это не гипотеза)

Три эксперимента на этой машине, тем же `node-pty` 0.13.1, реальным `zsh -i` в raw/ZLE-режиме
(186×50, как во вкладке из инцидента), мастер никогда не читается:

1. `sleep 100` вместо читателя — 325 МБ ушли через `fs.writeSync` без единой ошибки и задержки.
   Полностью пассивный процесс не создаёт backpressure на запись как таковой.
2. Реальный `zsh -i`, серия `fs.writeSync` по ~2000 байт — вернулась **частичная** запись:
   1022 → 977 → 900 → 859 → 818 → 763 → 738 байт, ни одной ошибки, ни одной задержки дольше
   миллисекунды. Очередь ядра заметно меньше 2 КБ и заполняется по мере игнорирования.
3. Прямая репродукция бага: `p.write()` одним куском в 6005 байт, мастер не читается — CPU
   процесса прыгает на 99–100% и держится там 12+ секунд, `setInterval`-heartbeat не срабатывает
   ни разу (событийный цикл полностью встал). Тот же сценарий через `fs.writeSync` с ручным
   ретраем остатка — CPU 42% → 5.6% → 0%, все heartbeat на месте, вся строка доставлена за 1.4 с.

## Дизайн

Новый модуль `pty-raw-write.js`, по образцу `pty-write.js` — чистые функции, `writeSync`/
`schedule` инжектируются, тест без реального pty:

```js
// writeAll(writeSyncFn, fd, buffer, schedule) -> Promise<{ ok: boolean, err? }>
//
// Пишет buffer в fd частями: каждый вызов writeSyncFn берёт сколько ядро приняло за раз,
// недописанный хвост уходит на следующий такт цикла через schedule (setImmediate) — а не
// доедается тем же вызовом, как это делает node-pty внутри uv_write2.
//
// EAGAIN/EWOULDBLOCK — тоже просто «попробовать ещё раз на следующем такте», не ошибка.
// Любая другая ошибка (EIO/EBADF — вкладку убили под запись) — ok:false, остаток бросаем,
// симметрично тому, как pty-write.js уже обходится с мёртвой вкладкой.
```

Точка врезки одна: `write` внутри `ptyOut = ptyWrite.makeWriter({...})` в `main.js` (~main.js:120).
Сейчас — `p.write(chunk); return true`. На POSIX (`process.platform !== 'win32'`, и только когда
`typeof p.fd === 'number'` — страховка на случай, если future-версия node-pty перестанет отдавать
fd) становится `return rawWrite.writeAll(fs.writeSync, p.fd, Buffer.from(chunk, 'utf8'),
setImmediate)`. Иначе (Windows, либо fd недоступен) — прежнее поведение, `p.write(chunk)`,
без изменений.

Windows не трогаем: там node-pty работает через conpty/именованный канал, модель совершенно
другая, ни одного инцидента там не было, а проверить fs.write на windows-fd я сейчас не могу —
нет машины. Если там всплывёт свой вариант той же болезни, это отдельная задача с собственной
проверкой.

Внешний слой (`pty-write.js` — очередь на вкладку, 256-байтный чанкинг, порядок печатей друг
относительно друга: Enter из телеграма не должен влезть в середину слова) не меняется вообще.
Меняется только то, что происходит ВНУТРИ одной записи одного куска — было "поручить node-pty",
стало "делать руками, с частичной записью, не блокируясь".

### Изменение контракта pty-write.js

Сейчас `write(key, chunk)` обязан вернуть `true`/`false` синхронно. Частичная запись может
растянуться на несколько тактов, поэтому `pump()` должен уметь ждать промис:
`Promise.resolve(write(key, chunk)).then(ok => ...)`. Существующие синхронные `write` (в том
числе все нынешние тесты) продолжат работать без изменений — `Promise.resolve(true)` резолвится
в тот же микротаск, поведение и порядок вызовов `schedule()` не меняются для синхронного случая.

### Диагностика

`pty-raw-write.js` ничего не логирует сам — он про доставку байт, не про журнал. Затяжную
доставку ловит обёртка в `main.js`: рядом с вызовом `writeAll` ставится `setTimeout` на 3000 мс
(вдвое больше худшего замера из живой проверки, ~1.4 с) и `writeAll(...).then(() =>
clearTimeout(t))`. Если таймер всё же сработал (промис за 3 с не разрешился), одна строка в
`restart.log` через существующий `restartLog`: «вкладка N: печать подвисла, читатель не
поспевает» — не более одного раза на кусок. Не останавливаем и не роняем очередь: если читатель
встал навсегда, вкладка и так нерабочая независимо от того, шлём мы в неё байты или нет.
Диагностика нужна только чтобы не охотиться за инцидентом заново вживую в следующий раз.
