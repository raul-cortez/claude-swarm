# Агрессивный порог перезапуска — design

Дата: 2026-08-31

**Пересмотрено 2026-09-01**: см. `2026-09-01-manual-restart-threshold-revert.md` — мягкий порог,
от которого здесь считается коэффициент, вернулся с baseline-формулы на ручной. Сам механизм
(печатать без паузы хода при высоком заполнении) не отменяется, только точка отсчёта под ним.

## Зачем

Просьбу о перезапуске сегодня можно напечатать только в конце хода — `askable()`
(`restart.js:521`) требует `turnOver(s)` (`restart.js:494`): статус `ready`/`waiting`, либо
`running` с фоновыми сабагентами. Причина разумная и явно записана в коде (`restart.js:483-493`):
не влезать в двадцатью строками просьбы в настоящую работу.

Проблема — ночью, на длинных автономных тасках, пауз может не быть подолгу: агент работает
десятки минут без остановки. Порог по контексту (`pctOver`, `restart.js:343`) — динамический,
свой для каждой вкладки (`2026-08-31-dynamic-restart-threshold-design.md`) — может быть пройден
давно, а спросить всё ещё не у кого: паузы просто не случилось. В худшем случае контекст
добирается до автосжатия раньше, чем находится момент спросить.

## Почему можно писать и во время running

В этом же разговоре проверили: печать в pty во время `running` технически безопасна. Во-первых,
это доказывает `tgAnswer` (`main.js:2728`) — телеграм-мост пишет в pty тем же способом, вообще
не спрашивая `turnOver`, и ничего не ломает. Во-вторых — сам Claude Code CLI внутри терминала
умеет ставить набранный (или впечатанный программой) текст в очередь, пока сам занят: показывает
его отступом под лоадером и отправляет как обычное следующее сообщение, когда освобождается.
С точки зрения агента печать во время running и печать в паузу неотличимы по результату —
разница только в том, что мы полагаемся на очередь CLI вместо своего собственного ожидания
паузы.

Это и снимает исходную причину ждать: `turnOver` был нужен не потому, что раньше нельзя было
печатать физически, а из соображений вежливости — не тратить ход на прерывание настоящей
работы. Для одного, крайнего случая (порог почти пройден до конца, окно вот-вот заполнится)
этой вежливостью можно пожертвовать.

## Идея: второй, более высокий порог, срабатывающий без паузы

Вместо одного порога — два:

- **Порог 1 (мягкий, как сегодня)** — `effectivePct(baselinePct, mult)`. Переход в фазу `asked`
  требует ЕЩЁ и `turnOver` — ждём паузу, как и сейчас.
- **Порог 2 (агрессивный, новый)** — тот же `effectivePct`, умноженный на коэффициент, без
  требования паузы. Печатается сразу, как только выполняются остальные условия (`hasBase`,
  `agentPresent`, `!boxOpen`, `uptimeMs`, `retryAt`) — `turnOver` из списка убирается только для
  этого пути.

Порог 2 всегда ≥ порога 1 (коэффициент > 1), поэтому к моменту его перехода порог 1 уже
пройден — отдельной гонки между ними нет.

## Формула

```
MAX_PCT = 60                        // было 75 — общий потолок для обоих порогов
soft     = effectivePct(baselinePct, mult)      // clamp(baselinePct × MULT, 15, 60)
aggr     = min(soft × AGGRESSIVE_MULT, MAX_PCT) // AGGRESSIVE_MULT = 1.5
```

`MAX_PCT` понижается с 75 до 60 — это правка того же файла, который сегодня же довела до конца
соседняя сессия (`2026-08-31-dynamic-restart-threshold-design.md`, коммит `187d4c3`). На момент
написания этой спеки в репозитории чисто, работа замёржена — конфликтовать не с чем.

Для тяжёлого проекта, у которого `soft` уже упёрся в потолок 60, `aggr` тоже даст 60 — оба
порога совпадут, и оба пути открываются одновременно. Это не баг, а следствие общего потолка:
разносить их дальше нет смысла — 60% уже выбран как достаточно ранняя точка.

## Что меняется в коде

Всё — внутри `restart.js`, `main.js` не трогаем: он уже передаёт `baselinePct`, `pct`, `status`,
`bg` в `restart.step()` (`main.js:5796-5813`), больше сигналов не нужно.

- `MAX_PCT`: `75` → `60` (`restart.js:25`).
- Новая константа `AGGRESSIVE_MULT = 1.5`.
- Новая функция `pctOverAggressive(s)`, рядом с `pctOver` (`restart.js:343`) — та же логика,
  умноженная на `AGGRESSIVE_MULT` и заклампленная в `MAX_PCT`.
- `askable()` (`restart.js:521`): вместо одного `if (!pctOver(s)) return false; ... if
  (!turnOver(s)) return false;` — развилка:
  ```
  if (pctOver(s) && turnOver(s)) return true;   // мягкий путь: порог + пауза
  if (pctOverAggressive(s)) return true;         // агрессивный путь: порог один, без паузы
  return false;
  ```
  Остальные проверки (`hasBase`, `agentPresent`, `boxOpen`, `uptimeMs`, `retryAt`) остаются
  общими для обоих путей — ровно тем же кодом, что и сегодня.

Дальше по автомату ничего не меняется: переход в `asked`, текст просьбы (`askText`), ожидание
файла-ответа, `MAX_SILENT`, отсрочки — всё общее для обоих путей. Агрессивный порог — это только
другое условие ВХОДА в уже существующий разговор, не новая ветка автомата и не новый текст.

## Что не делаем

- **Не добавляем жёсткий гейт на Task/подагентов.** Обсуждали — решили, что для контекста
  достаточно перестать ждать паузы; блокировать новые сабагенты (как это устроено для
  `rate_limits`) не нужно.
- **Не пишем отдельный текст просьбы для агрессивного пути.** Агент не должен видеть разницы
  между «дождались паузы» и «не дождались» — с его стороны это неотличимо от того, что кто-то
  написал сообщение, пока он был занят (ровно то поведение CLI, которое разобрали выше).
- **Не трогаем `main.js`.** Единственное место правки — `restart.js`; никаких новых сигналов,
  тактов или IPC не требуется.

## Тесты

`test/restart.test.js`: новые кейсы для `pctOverAggressive` (клампится в `MAX_PCT`, использует
тот же `baselinePct`/`mult`, что и `pctOver`) и для `askable()` — агрессивный порог пройден,
`turnOver` ложный → всё равно `true`; мягкий порог не пройден вовсе → `false` даже если бы
`turnOver` был истинным (защёлка не должна открыться раньше времени). Существующие кейсы на
`MAX_PCT=75` в `effectivePct` (`test/restart.test.js:17-20`) переписываются на `60`.

## Открытые вопросы

- `AGGRESSIVE_MULT=1.5` и новый `MAX_PCT=60` подобраны в разговоре, не по статистике — как и
  `DEFAULT_MULT=7` у соседней спеки, могут потребовать пересмотра после того, как накопятся логи
  реальных перезапусков.
